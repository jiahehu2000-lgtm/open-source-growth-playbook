# 如何观察点星变化

## 指标不要混在一起

| 指标 | 回答的问题 | 不能直接证明什么 |
|---|---|---|
| 累计 GitHub Stars | 截至采样有多少账号收藏 | 最近增长、实际使用或代码质量 |
| 同仓库两个时间点的净 Star 变化 | 这个窗口数量增减多少 | 变化由某一篇帖子造成 |
| Trending 页面标出的本日 / 周 / 月增星 | 榜单页面给出的对应周期信号 | 官方方向排名或未来增长 |
| HN points / comments | 帖子获得多少投票与讨论 | GitHub点星转化、正面评价比例 |
| GitHub views / unique visitors / full clones | 访问与下载活动 | 活跃用户、留存或全部访问来源 |

## 不需要凭据的最小观察

在修改前运行 Skill 的 `scripts/github_snapshot.py capture`，改变后在明确日期再次运行。`compare` 验证仓库身份和时间顺序，输出净 Star / fork 差值以及两个快照的时间跨度。

第一次采样只是基线。没有后续采样时应写“已准备观察方法”，不能写“已提高点星量”。净增长可以为负；接口失败应记录失败，不填 0。不要把不同仓库或不同采样窗口拼成前后对比。

## 有仓库权限时补充访问数据

按 [GitHub官方文档](https://docs.github.com/en/repositories/viewing-activity-and-data-for-your-repository/viewing-traffic-to-a-repository)，有 push 权限的人可在 Insights → Traffic 查看过去14天的访问、完整clone、来源与热门内容。访问 / clone 按小时更新，来源和热门内容按日更新，时区为 UTC。

及时保存同一时间窗口的记录，超过保留窗口后可能无法完整补齐。使用已授权的 GitHub 工具，不提取用户凭据。

如果计算“净新增 Star ÷ 独立访客”，把它标为观察代理指标。Star净差包含取消收藏，访客可能跨日重复、从其他渠道进入；这不是精确的个人转化率，也不是渠道归因。

## 怎样做下一轮调整

- 访问少：检查方向是否与读者相关、标题是否具体、入口是否容易找到。
- 有访问但少人开始：检查依赖、演示、安装步骤和最小样例。
- 有人运行但反馈多：优先修复真实问题，再讲述改进。
- 只有Star没有使用证据：补充讨论和使用反馈，不把收藏数当成研究或性能结论。

先记录改动日期和内容，在可比较的窗口看变化。发布时间、读者来源、项目成熟度等同时变化时，结论只能写相关性；不要为了凑目标Star数挑选观察窗口。
