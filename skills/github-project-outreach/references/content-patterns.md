# 内容设计与渠道选择

这些是高互动项目中观察到的表达方式，不是保证增长的算法。

## 先决定：谁会因为哪个结果使用它？

| 项目类型 | 读者先关心什么 | 适合先展示什么 |
|---|---|---|
| 科研工具 | 能否处理我的数据、导出后能否继续改 | 真实图例、可编辑产物、最小数据和运行命令 |
| AI / Agent 工具 | 能完成哪一件具体任务、需要什么模型与权限 | 从输入到输出的短演示、失败边界、费用与环境条件 |
| 数据可视化 | 可读性、交互体验、在什么条件下流畅 | 可操作示例、数据规模和设备明确的性能测量 |
| 本地 / 自托管应用 | 数据放在哪里、部署是否容易 | 本地安装入口、架构说明、已有集成 |
| 教学项目 | 能否让我看懂一个难点 | 可操作小实验、图解与反馈 |
| 硬件项目 | 做出了什么、能否复刻 | 实物视频、设计文件、物料和测量说明 |

## README 的可选骨架

按项目选择，不强求所有模块：

1. 一句话：目标读者 + 具体任务 + 可验证产物。
2. 一个真实预览或可运行示例，写清数据与条件。
3. 最短上手路径，注明依赖、平台、许可。
4. 读者按目标能找到的教程 / API / 示例入口。
5. 当前能力与重要限制、反馈入口。
6. 温和的一句话 Star 提示，文档和下载仍直接可用。

徽章链接到真实的 CI、许可或动态指标。装饰性“热门”“高性能”图案不能冒充测量。不要生成不存在的用户评价或论文背书。

## 中文短帖：先说具体用途

可用的结构是“我遇到的问题 → 做出的工具 → 一次具体演示 → 怎么试 → 条件 → 反馈入口”。标题备选应分别强调不同价值，例如可编辑、离线可用、一个具体任务；不堆砌无关热门词。

简短示例：

> 我把整理科研图的流程做成了工具。给出数值数据和参考图，可以调用本机 Origin 绘制并保存 OPJU 工程；还支持把图嵌入 PPT，后面双击继续改。仓库里有合成数据演示和中文安装步骤。需要 Windows 和本机 Origin。欢迎试用并反馈最需要的图型；有帮助也欢迎 Star。

这是表达格式示例；实际生成前必须核对项目能力。不要复制其他作者的图、品牌或措辞。针对用户提供的科研数据，先生成脱敏或合成演示素材。

## 技术社区：减少读者验证成本

展开的是实质内容：为什么已有方案没有满足需求、实现如何工作、可以运行的命令、与合理基线的比较、已知限制。性能比较使用相同任务与说明过的设备，比较公平时再突出差异。

“有人讨论 / 感兴趣”与“有人实际使用 / 点星”分别记录。批评中出现的障碍可以作为下一轮改进依据，例如缺少最小样例、安装需要未说明的账户、API 对比不公平。

## Hacker News 的特殊处理

截至 2026-10-09，官方 [HN guidelines](https://news.ycombinator.com/newsguidelines.html) 禁止生成或 AI 编辑的文本和自动发帖，并禁止拉票。官方 [Show HN guidelines](https://news.ycombinator.com/showhn.html) 要求可体验的作品，清单与博客不适合 Show HN。

因此对 HN 输出“作者准备材料”：真实能力、演示链接、已知限制、需要作者自己解释的设计取舍，以及该项目是否满足 Show HN 条件。不要代写最终投稿或评论，不向作者的朋友索取投票。下一次使用前检查规则是否改变。

## GitHub 本身怎样展示

使用相关的简介、Topics、README、示例和Release。有实质代码或内容的仓库可以附相关项目链接；避免到别人的 Issues 留无关宣传。[GitHub Acceptable Use Policies](https://docs.github.com/en/site-policy/acceptable-use-policies/github-acceptable-use-policies) 明确限制虚假互动、自动点星和过量批量推广。
