## 1. AI 编码与代码审查

**读者要解决什么：**读者关心代码究竟哪里有问题，能否减少重复审查。

**可做的小项目：**科研 Python 检查助手：检查单位、随机种子和训练测试分离，并输出具体行号。

**第一份演示：**一份含已知问题的小脚本、检查结果、人工核对说明，以及修正前后差异。

**介绍怎么写：**用一个实际漏检问题进入介绍，再解释规则检查与模型判断各负责什么。

**要讲清的限制：**检测准确性需要标注样本验证；不能把‘AI审查’写成自动保证代码正确。

参考 [alibaba/open-code-review](https://github.com/alibaba/open-code-review)；[API 核验](https://api.github.com/repos/alibaba/open-code-review)时间 `2026-10-09T09:41:45Z`；[月榜来源](https://github.com/trending?since=monthly)时间 `2026-10-09T09:41:44Z`。

## 2. 专业 Agent Skills 与插件

**读者要解决什么：**读者希望让已有 AI 助手可靠完成一项具体工作。

**可做的小项目：**Origin 绘图、论文表格整理、实验日志检查等边界清楚的专用 Skill。

**第一份演示：**安装位置、一次真实调用、输入文件、可编辑输出，以及支持软件版本。

**介绍怎么写：**让读者先看到最终文件，再用最短步骤得到同类结果。

**要讲清的限制：**Skill、依赖软件和外部服务要分别说明；有 Skill 不等于包含商业软件许可证。

参考 [mattpocock/skills](https://github.com/mattpocock/skills)；[API 核验](https://api.github.com/repos/mattpocock/skills)时间 `2026-10-09T09:41:45Z`；[周榜来源](https://github.com/trending?since=weekly)时间 `2026-10-09T09:41:42Z`。

## 3. 多 Agent 协作与任务编排

**读者要解决什么：**读者需要把复杂工作分给不同角色，并知道任务进度和失败位置。

**可做的小项目：**一个‘查资料—写代码—独立验证’三角色工具，保留输入、输出与交接记录。

**第一份演示：**同一个小任务的分工过程、最终交付和一次失败恢复；写明模型调用与成本条件。

**介绍怎么写：**展示角色之间如何交接，比画一张复杂架构图更容易理解。

**要讲清的限制：**角色多不自动等于效果更好；比较时应保持任务、模型和预算条件一致。

参考 [paperclipai/paperclip](https://github.com/paperclipai/paperclip)；[API 核验](https://api.github.com/repos/paperclipai/paperclip)时间 `2026-10-09T09:41:46Z`；[月榜来源](https://github.com/trending?since=monthly)时间 `2026-10-09T09:41:44Z`。

## 4. Agent 记忆与上下文管理

**读者要解决什么：**读者不想反复解释项目背景，也需要知道回答引用了哪条旧记录。

**可做的小项目：**本地实验记录检索工具：带日期、来源、过期提示和可纠正的项目决定。

**第一份演示：**跨两次会话找回一个真实决定，并展示来源和人工修订。

**介绍怎么写：**用‘上次说过什么、这次如何找回’的对照，说明保存、检索和更新的区别。

**要讲清的限制：**存储更多不保证检索正确；旧记录不能当作当前事实。

参考 [vectorize-io/hindsight](https://github.com/vectorize-io/hindsight)；[API 核验](https://api.github.com/repos/vectorize-io/hindsight)时间 `2026-10-09T09:41:47Z`；[月榜来源](https://github.com/trending?since=monthly)时间 `2026-10-09T09:41:44Z`。

## 5. 私有文档 RAG 与知识库

**读者要解决什么：**读者要从自己的文档得到可以追溯出处的答案。

**可做的小项目：**面向一个细分学科的公开文献问答示例包，保留页码、版本和无法回答的例子。

**第一份演示：**一份允许再分发的文档、一个问题、检索段落与答案出处。

**介绍怎么写：**先展示‘答案来自哪一页’，再解释索引和检索方法。

**要讲清的限制：**检索命中文档不等于答案正确；文档许可、外部模型调用和数据去向要说明。

## 6. 桌面自动化与受限运行环境

**读者要解决什么：**读者想让 AI 操作已有软件，并明确能访问哪些文件和应用。

**可做的小项目：**固定科研软件的批量导出与检查工具，生成操作日志和失败提示。

**第一份演示：**从输入文件到导出文件的连续过程，以及操作范围和失败时的处理。

**介绍怎么写：**展示一个完整小任务，用实际步骤说明价值和权限范围。

**要讲清的限制：**桌面状态、版本和文件锁会影响自动化；不能只放一次成功截图。

## 7. 可编辑图形与视频工作流

**读者要解决什么：**读者希望快速得到能继续修改的图形、动画或视频。

**可做的小项目：**实验流程 SVG、数据动画、Origin 到可编辑 PPT 的工作流。

**第一份演示：**最终画面、源文件，以及改变一个参数后重新导出的过程。

**要讲清的限制：**视觉好看不保证科学准确；区分示意图、实测数据和仿真结果。

## 8. 本地语音与音视频处理

**读者要解决什么：**读者想在本机完成转写、字幕、配音或术语修正。

**可做的小项目：**讲座录音转字幕工具，附专业术语词表和时间戳核对入口。

**第一份演示：**经授权的短音频、输出字幕、运行环境和已知转写错误。

**介绍怎么写：**展示一个完整片段和可下载输出，而非只列支持语言数量。

**要讲清的限制：**模型、硬件和下载大小决定使用门槛；语音使用应有授权。

## 9. 低门槛本地模型推理

**读者要解决什么：**读者想知道自己的设备能运行什么，以及需要多长时间和多少资源。

**可做的小项目：**本地模型环境诊断工具，输出明确版本与实际测量的运行报告。

**第一份演示：**设备规格、模型版本、加载耗时、内存占用和实际输入输出。

**介绍怎么写：**围绕‘我的电脑能不能用’展开，把可复现环境放在数字旁。

**要讲清的限制：**能加载模型与可接受速度是两回事；项目作者的性能承诺需独立测量。

## 10. 实时数据地图与空间可视化

**读者要解决什么：**读者想把复杂位置数据变成可交互、可核对的画面。

**可做的小项目：**公开天气、交通或实验采样点位地图，标注来源、时间和缺失值。

**第一份演示：**一个可操作地图、一次时间筛选和一个点位的原始来源。

**介绍怎么写：**先让读者探索，再解释数据怎么来、多久更新、哪里不完整。

**要讲清的限制：**‘实时’应有更新间隔和数据延迟定义；视觉效果不能掩盖数据缺失。

## 对现有 Origin / RC 项目的启发

- Origin 项目最贴近“专业 Skill＋可编辑视觉”：先展示 OPJU、矢量图和可编辑 PPT，再解释软件要求与最短操作流程。
- RC 项目适合突出“有出处的数据＋可复现的计算流程”：展示真实的运行输入、输出、训练测试分离及模型适用范围。
- 给科研读者的价值是文件可用、计算可复现、方法可检查。主页改进本身不证明准确率提高，也不证明 Stars 已增长。
